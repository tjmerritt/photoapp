photoapp API Reference

photoapp API Reference

This document describes every HTTP endpoint exposed by the photoapp backend (internal/handlers/router.go), organized by resource category. For each endpoint it covers required inputs (path parameters, query parameters, headers, cookies, and request bodies), the shape of successful responses, every distinct error condition the handler can return, and notable side effects or business rules.

Generated directly from the Go source (handlers, models, middleware, and the permissions package) as of the current main branch. Where the underlying code has quirks, inconsistencies, or unusual behavior, this document calls them out explicitly rather than smoothing them over.

Global conventions

These rules apply to every endpoint unless a specific endpoint’s section says otherwise.

Middleware chain. Every request passes through, in order: RequestID → CORS → Exhibition → Auth → Logger → the router itself.

  • RequestID generates a UUID and sets it on the X-Request-ID response header, and stores it in context for logging.
  • CORS sets Access-Control-Allow-Origin: *, Access-Control-Allow-Methods: GET, POST, PUT, PATCH, DELETE, OPTIONS, and Access-Control-Allow-Headers: Content-Type, X-User-ID. OPTIONS requests receive an immediate 204 No Content.
  • Exhibition resolves the request’s Host header against exhibition_hostnames (trying the full host:port first, then the bare hostname). If the hostname is unrecognized, the middleware serves newdomain.html (cached in memory, refreshed at most every 60 seconds) with a 200 status to every request path, including API calls — this affects all endpoints, not just page loads. If recognized, it sets the exhibition ID in the request context (middleware.ExhibitionID(ctx)); an empty exhibition ID means global scope (used by some admin/org-picker endpoints).
  • Auth resolves a user identity from, in priority order: (1) the photoapp_session cookie, looked up against the sessions table, or (2) — only when no valid session cookie is present — a fallback header (default name X-User-ID, configurable via the AUTH_HEADER environment variable / cfg.AuthHeader), used for local development and testing. This middleware does not reject unauthenticated requests; it simply leaves the context’s user ID empty if no identity is found. Rejection happens per-route.

Authentication enforcement. Routes under /api/v1/... that require login are wrapped in a small auth(...) helper (router.go) that checks for a resolved user ID and, if absent, immediately returns 401 with body {"error":"authentication required"} before the handler runs. Routes under /auth/... are never wrapped in this helper — each auth handler performs its own internal check (via middleware.UserID(ctx)) and decides for itself whether to require a logged-in caller.

Response envelopes. - Errors: every handler that fails calls middleware.WriteError(w, status, message), which always produces {"error": "<message>"} with Content-Type: application/json. - Success: middleware.WriteJSON(w, status, value) marshals value directly to JSON with Content-Type: application/json. There is no single universal success envelope — list endpoints generally return {"total", "offset", "limit", "<items-key>": [...]}, but the exact shape is documented per endpoint below.

Static/non-API routes. GET /uploads/*filepath serves uploaded emoji images directly from cfg.UploadDir. Any other unmatched path outside /api is served from cfg.AppDir via a standard file server (the frontend single-page app). Unmatched paths under /api/* return 404 {"error":"not found"}.

Health check. GET /healthz returns 200 {"status":"ok"} with no authentication and no permission checks (still passes through the Exhibition middleware like every other route).

Photos, Search & Media

Covers GET /api/v1/photo, GET /api/v1/photos, GET /api/v1/user, PATCH /api/v1/photo, GET /api/v1/search, POST /api/v1/photos/upload, GET /avatars/:hash, and GET /api/v1/imgproxy.

GET /api/v1/photo

Category: Photos Auth: optional. Registered via r.HandlerFunc(http.MethodGet, "/api/v1/photo", photos.ServeHTTP) — no auth(...) wrapper, and note this route bypasses httprouter’s Params (registered with HandlerFunc, not GET), so there are no path parameters even though the doc comment says ?photoid=. Unauthenticated callers can still see any photo that is Public-labeled (or accessible via an indirect Display/Gallery grant to Public/LoggedIn-less entities); private photos are hidden unless the caller is the owner or holds PrivatePhotoView. Permissions: Checks permissions.PermPrivatePhotoView → canSeePrivate and permissions.PermPhotoView → hasPhotoView (both checked at exhibition scope, galleryID/resourceType/resourceRef=""). Visibility rule (from internal/permissions/permissions.go’s “Photo visibility” doc, reproduced exactly):

A photo is visible to a caller iff: caller is the photo’s owner, OR ( (caller holds PhotoView directly [exhibition/org/global] OR caller holds DisplayView/GalleryView covering a display currently showing the photo — see photoAccessibleViaDisplaySQL in fetch.go) AND (photo has a Public/True label OR caller holds PrivatePhotoView) ).

Holding PrivatePhotoView alone (without PhotoView, direct or indirect) grants nothing. The owner exception exists specifically so a user who just uploaded a photo (uploads are always created private) can still see their own photo even without PhotoView/PrivatePhotoView.

Path parameters: none (query-string only; not an httprouter route).

Query parameters: - photoid (string, required unless random=true/1) — UUID of the photo to fetch. - random (string, optional) — "true" or "1" selects a uniformly random visible photo instead of a specific photoid. When set, photoid may be omitted. - label (string, optional) — a labelid; when present, the related array is computed via fetchRelatedByLabel (photos sharing the same label name+value) instead of the default fetchRelated (the photo’s related_photos table rows).

If both photoid and random are absent/false → 400.

Headers: X-User-ID (dev auth fallback, handled by global Auth middleware). No endpoint-specific headers read directly.

Cookies: photoapp_session applies globally.

Request body: none.

Response — success: 200 OK, JSON body is models.Photo:

{
  "photoid": "string",
  "image": { "url": "string", "width": 0, "height": 0 },
  "title": { "text": "string", "userid": "string", "username": "string", "canedit": false },
  "description": "string",
  "labels": [ { "labelid": "string", "name": "string", "value": "string", "userid": "string", "username": "string", "color": "string?", "restricted": false } ],
  "labelsurl": "string? (omitempty)",
  "emojis": [ { "emojiid": "string", "emoji": "string?", "imageurl": "string?", "alttext": "string", "count": 0, "users": [ { "id":"string","name":"string","tn":"string?" } ], "usersurl": "string? (omitempty)" } ],
  "emojisurl": "string? (omitempty)",
  "related": [ { "photoid": "string", "imageurl": "string", "clickurl": "string", "width": 0, "height": 0 } ],
  "comments": [ { "commentid": "string", "author": { "userid":"string","username":"string","tn":"string?" }, "date": "RFC3339", "replycount": 0, "comment": "string", "deleted": false, "repliesurl": "string" } ],
  "commentsurl": "string? (omitempty)"
}

labels is capped at first 10 (labelLimit), with labelsurl set to /api/v1/labels?photoid=...&limit=10&offset=10 if more exist. emojis is capped at first 20, each with up to 3 users (emojiUserLimit); emojisurl/per-emoji usersurl set similarly when truncated. comments capped at first 10 top-level comments; commentsurl set when more exist. Image URLs are rewritten via proxyImageURL (external http(s):// URLs become /api/v1/imgproxy?url=...).

Response — errors: - 400 Bad Request — "photoid is required" (neither photoid nor random given). - 404 Not Found — "photo not found" (no row, or row invisible per the visibility rule — pgx.ErrNoRows). - 500 Internal Server Error — "db error" on any DB failure (initial query, fetchLabels, fetchEmojis, fetchRelated/fetchRelatedByLabel, fetchComments).

Notes: - Side effect: unconditionally executes UPDATE photos SET view_count = view_count + 1 WHERE photoid = $1 AND (...) after the photo row is fetched successfully — increments the view counter on every successful fetch (result ignored, errors swallowed). - title.canedit is true only when currentUser != "" and currentUser equals either the title-setter’s userid or the photo owner’s userid. - Related-photos query differs based on presence of label query param (fetchRelatedByLabel vs fetchRelated), both independently re-apply the full visibility rule per candidate row plus the owner exception.

GET /api/v1/photos

Category: Photos Auth: optional. Registered as r.GET("/api/v1/photos", photoList.ServeHTTP) — no auth(...) wrapper. Unauthenticated callers only see Public-labeled (or indirectly Display/Gallery-accessible) photos; authenticated callers additionally see their own private uploads and, if they hold PrivatePhotoView + PhotoView (direct or indirect), all private photos in scope. Permissions: Same rule as GET /api/v1/photo (PermPrivatePhotoView and PermPhotoView, exhibition-scoped) — owner OR ((PhotoView direct-or-indirect) AND (Public label OR PrivatePhotoView)).

Path parameters: none.

Query parameters: - limit (int, optional, default 40) — must parse as int, >0 and <=100, otherwise the default is silently kept. - offset (int, optional, default 0) — must parse as int >=0, otherwise default kept.

Headers: X-User-ID dev fallback via global middleware.

Cookies: photoapp_session applies globally.

Request body: none.

Response — success: 200 OK, JSON body is models.PhotoListResponse:

{
  "total": 0,
  "offset": 0,
  "limit": 0,
  "photos": [ { "photoid": "string", "imageurl": "string", "width": 0, "height": 0 } ]
}

Ordered by created_at DESC, photoid. total comes from a COUNT(*) OVER() window function over the visibility-filtered set (i.e., the total across all pages, not just the returned page). Image URLs proxied via proxyImageURL.

Response — errors: - 500 Internal Server Error — "db error" on query, scan, or row-iteration failure. - (No 400 case: invalid limit/offset values are silently ignored in favor of defaults, not rejected.)

Notes: No side effects (does not increment view_count). This is the “exhibition wall” listing endpoint.

GET /api/v1/user

Category: Users Auth: none required and no permission checks at all — fully public endpoint (any caller, authenticated or not, can look up any non-deleted user by ID). Registered with r.HandlerFunc(http.MethodGet, "/api/v1/user", users.ServeHTTP), no auth(...) wrapper. Permissions: none checked.

Path parameters: none.

Query parameters: - userid (string, required) — UUID of the user to fetch.

Headers: none endpoint-specific (global Auth middleware still runs but its result is unused by this handler).

Cookies: photoapp_session applies globally but is irrelevant here (handler never reads middleware.UserID).

Request body: none.

Response — success: 200 OK, JSON body is models.User:

{
  "userid": "string",
  "username": "string",
  "profile": {
    "fullname": "string",
    "joined": "RFC3339 timestamp",
    "link": "string?",
    "image": "string?"
  }
}

profile.image defaults to '/avatars/' || md5(lower(trim(COALESCE(email, userid)))) when profile_image is NULL in the DB (i.e. a generated SVG avatar URL under /avatars/:hash).

Response — errors: - 400 Bad Request — "userid is required" (missing/empty userid query param). - 404 Not Found — "user not found" (no matching non-deleted row — pgx.ErrNoRows). - 500 Internal Server Error — "db error" on any other DB failure.

Notes: Only returns non-deleted_at users (soft-deleted users appear as 404). No image proxying applied here (unlike photo/emoji image URLs elsewhere) — the avatar URL is already a relative same-origin path.

PATCH /api/v1/photo

Category: Photos Auth: required. Registered as r.PATCH("/api/v1/photo", auth(...)) — the auth wrapper checks middleware.UserID(ctx) and returns 401 with {"error":"authentication required"} before the handler ever runs if there’s no resolved user. The handler itself also independently re-checks and would return the same 401/message if reached without a user. Permissions: No visibility check is performed. Edit authorization: allowed if currentUser == ownerID OR currentUser == titleUserID (the user who currently owns/set the title, defaulting to the photo owner if never explicitly set) — OR, if neither, the caller must hold permissions.PermPhotoDescriptionModify (checked at the exhibition scope resolved from the photo’s own exhibition via resolvePhotoExhibition), otherwise 403.

Path parameters: none (query string based, not an httprouter path param).

Query parameters: - photoid (string, required) — UUID of the photo to update.

Headers: X-User-ID dev fallback via global Auth middleware; Content-Type: application/json expected for the body.

Cookies: photoapp_session applies globally — this is the primary way currentUser gets set for this write endpoint.

Request body: models.UpdatePhotoTitleRequest:

{ "title": "string" }

title is trimmed of whitespace server-side; empty after trimming → 400.

Response — success: 200 OK, JSON body:

{ "title": "string" }

(a plain map[string]string{"title": title}, not a models.* struct).

Response — errors: - 400 Bad Request — "photoid is required" (missing query param). - 401 Unauthorized — "authentication required" (no resolved user). - 400 Bad Request — "invalid JSON body" (body doesn’t decode as UpdatePhotoTitleRequest). - 400 Bad Request — "title must not be empty" (title is empty/whitespace-only after strings.TrimSpace). - 404 Not Found — "photo not found" (no non-deleted photo with that ID). - 403 Forbidden — "not allowed to edit this title" (caller is neither owner nor title-setter, and lacks PermPhotoDescriptionModify). - 500 Internal Server Error — "db error" on any DB failure (the initial ownership lookup or the final UPDATE).

Notes: On success, updates photos.title_text, photos.title_userid (set to the editing user, i.e. editing reassigns “who titled this”), and photos.updated_at = NOW(). Only the title field is mutable here — despite the handler doc comment mentioning “title/description,” only title is actually accepted/updated by this endpoint (no description field in UpdatePhotoTitleRequest).

GET /api/v1/search

Category: Search Auth: optional. Registered as r.HandlerFunc(http.MethodGet, "/api/v1/search", search.ServeHTTP), no auth(...) wrapper. Unauthenticated callers only get Public-labeled/indirectly-accessible results; authenticated callers additionally get their own private photos plus, if permission-eligible, all private photos in scope — same visibility formula as /api/v1/photo. Permissions: permissions.PermPrivatePhotoView (canSeePrivate) and permissions.PermPhotoView (hasPhotoView), both exhibition-scoped, applied identically to the /api/v1/photo visibility rule as a WHERE clause on every candidate photo.

Path parameters: none.

Query parameters: - q (string, optional) — the raw search query string. Empty/whitespace-only → returns an empty result set (not an error).

Query language (parsed by parseSearchQuery, whitespace-tokenized via strings.Fields, case-insensitive by lowercasing every token):

Qualifier Meaning
@username Photos the user has interacted with (commented, labeled, or emoji-reacted)
user:@username or user:username Same as @username
label:Name Photos with a label whose name matches Name (substring, case-insensitive); if no label anywhere matches by name, falls back to matching by value instead
label:Name=Value Photos with a label matching both Name and Value (both substring/ILIKE)
Name:Value (shorthand) Same as label:Name=Value, unless Name is a reserved prefix (user, label, emoji, comment, title, desc, description — in which case it’s parsed as that qualifier instead, or ignored if the value half is empty)
emoji:Name Photos with an emoji reaction whose alt_text matches Name
comment:Text Photos with a non-deleted comment whose text matches Text
title:Text Photos whose title_text matches Text
desc:Text or description:Text Photos whose description matches Text
any other token Free text — scored (not filtered) across title (×4), description (×3), label name/value (×2), emoji alt-text (×2), comment text (×1); duplicates de-duplicated

All qualifiers are combinable (ANDed as INNER JOINs); free-text terms are OR-scored via a CTE and only included if sort_score is positive. If the parsed query ends up empty, the response is also an empty result set.

Headers: X-User-ID dev fallback via global middleware.

Cookies: photoapp_session applies globally.

Request body: none.

Response — success: 200 OK, JSON body is models.SearchResponse:

{
  "query": "string (echoes input q, or \"\" if empty)",
  "total": 0,
  "results": [ { "photoid": "string", "imageurl": "string", "width": 0, "height": 0, "title": "string" } ]
}

Results ordered by relevance score (free-text hits) descending, then created_at DESC, then photoid; hard-capped at 13 rows (LIMIT 13) — no pagination parameters exist for this endpoint. total is simply len(results) (i.e., capped at 13, not a true total count). Image URLs proxied via proxyImageURL.

Response — errors: - 500 Internal Server Error — "db error" on query execution, scan, or row-iteration failure. - No 400 responses — an empty/unparseable query returns 200 with empty results rather than an error.

Notes: No side effects. All qualifier value matching uses SQL ILIKE '%...%' (case-insensitive substring), not exact match or full-text search ranking beyond the simple weighted-count scoring described above.

POST /api/v1/photos/upload

Category: Photos Auth: required. Registered as r.POST("/api/v1/photos/upload", auth(uploads.ServeHTTP)). Permissions: permissions.PermPhotoCreate, exhibition-scoped. If the check errors or returns false → 403 Forbidden.

Path parameters: none.

Query parameters: none.

Headers: X-User-ID dev fallback via global Auth middleware; request must be multipart/form-data.

Cookies: photoapp_session applies globally.

Request body: multipart form with: - files (one or more file parts, field name exactly "files") — required; each is an independent image upload. Accepted content types (sniffed via http.DetectContentType, not filename extension): image/jpeg → .jpg, image/png → .png, image/gif → .gif. WebP is deliberately not accepted here (unlike other upload endpoints) because photos require real pixel dimensions and Go’s stdlib has no built-in WebP decoder. - labels (optional form text field) — a JSON array string of {"name": "...", "value": "..."} objects (models.AddLabelRequest), applied to every photo in the batch in addition to each photo’s own EXIF-derived labels. Entries with empty name or value are silently skipped.

Multipart body is parsed with maxUploadMemory = 32 << 20 (32 MB) held in memory before the reader spills additional file parts to the OS temp dir — this is not a hard total-size cap.

Response — success: 200 OK (always 200, even for files whose uploads fail individually), JSON body is models.UploadPhotosResponse:

{
  "results": [
    { "filename": "string", "photoid": "string (omitempty)", "status": "ok|error", "error": "string (omitempty)" }
  ]
}

One UploadResult per submitted file, in submission order; status: "ok" entries have photoid populated, status: "error" entries have error populated with the failure message.

Response — errors (request-level, before any per-file processing): - 403 Forbidden — "you do not have permission to upload photos" (caller lacks PermPhotoCreate, or the permission check itself errored). - 400 Bad Request — "could not parse multipart form" (r.ParseMultipartForm failed). - 400 Bad Request — `"labels" must be a JSON array of {"name","value"} objects` (the labels form field, if present and non-empty, fails to unmarshal). - 400 Bad Request — `no files provided (use multipart field "files")` (the files field had zero file parts). - (No request-level 500 — DB/file errors are captured per-file inside results[i].error, not surfaced as an HTTP 500.)

Per-file error messages (inside results[i].error, status: "error", HTTP status remains 200 for the overall response): - "opening upload: %w" — failed to open the uploaded file handle. - "reading upload: %w" — failed to read file bytes. - `unsupported image type "%s" (only JPEG, PNG, and GIF are accepted)` — content-type sniff didn’t match the allow-list. - "could not read image dimensions: %w" — dimension parsing failed. - "creating upload directory: %w" — os.MkdirAll failed. - "saving file: %w" — os.WriteFile to disk failed. - "starting transaction: %w" — DB transaction begin failed. - "inserting photo: %w" — the INSERT INTO photos failed. - "inserting label %q: %w" — an individual label INSERT INTO labels failed (aborts remaining labels for that photo). - "marking label names restricted: %w" — photoimport.MarkNamesRestricted failed. - "committing: %w" — transaction commit failed.

Notes (side effects and business rules): - Each file is saved to disk at <Cfg.UploadDir>/<uuid>.<ext> with permissions 0o644; the on-disk filename is a fresh UUID, unrelated to the original filename (original filename preserved as a Filename label and in the response’s filename field). - If any step after the disk write fails, the just-written file is deleted so no orphaned file remains without a corresponding DB row. - The DB insert (photo row + all labels + MarkNamesRestricted bookkeeping) happens inside a single transaction — a photo is never committed without its labels or vice versa. - Every uploaded photo automatically gets: an EXIF-derived label set, plus computed labels Resolution ("<w>x<h>"), Filename (original filename), and Public = "False" (uploaded photos are always private by default — no is_public column exists anymore; visibility is entirely label-driven), plus any batch labels from the request. Filename/Resolution are reordered to appear first among labels so they always show on the photo detail page’s first label page (limit 10). - The photo’s title_text is auto-derived from the original filename (strips extension, capitalizes dash/underscore/space-separated words) and title_userid is set to the uploader. - The new photo’s owner_userid is the uploading user; exhibitionid is set from the request context (nullable). - This endpoint deliberately does not run face detection (unlike cmd/import-photos), since that depends on a native OpenCV/gocv dependency not linked into the main server binary. - Every label name seen (EXIF-derived + computed names) is marked “restricted” the first time it’s encountered — but this never overwrites an existing label_names row, so an admin’s prior explicit un-restriction of a name persists across future uploads.

GET /avatars/:hash

Category: Avatars (static/generated assets) Auth: none — fully public, unauthenticated. Registered as r.GET("/avatars/:hash", ServeAvatar), no auth(...) wrapper, and the handler reads no user/session state at all. Permissions: none.

Path parameters: - hash (httprouter param :hash) — typically the lowercase MD5 hex digest of a trimmed, lowercased email address. Not validated as an actual MD5 — any non-empty string is accepted and passed straight to the avatar generator.

Query parameters: none.

Headers: none read.

Cookies: none read.

Request body: none.

Response — success: 200 OK, Content-Type: image/svg+xml — raw SVG bytes generated deterministically from hash. Same hash always produces the same image (deterministic).

Response — errors: - 404 Not Found (plain http.NotFound, not the JSON middleware.WriteError format) — when hash is empty.

Notes: Sets Cache-Control: public, max-age=31536000, immutable (1 year, immutable) — safe because the same hash always yields the same deterministic SVG. No DB access at all in this handler.

GET /api/v1/imgproxy

Category: Image proxy Auth: none — fully public, unauthenticated. Permissions: none — this endpoint proxies arbitrary external image URLs without any authorization check; the only restriction is the URL scheme allow-list below.

Path parameters: none.

Query parameters: - url (string, required) — the external image URL to proxy. Must start with http:// or https://; anything else (or empty) is rejected. - w (int, optional) — target width in pixels for on-the-fly downscaling. If omitted or ≤0, the original image is served unmodified.

Headers: none endpoint-specific read.

Cookies: none read.

Request body: none.

Response — success: 200 OK, non-JSON — raw image bytes. - If w is set and a previously-cached scaled variant exists: serves cached bytes, Content-Type: image/jpeg, header X-Cache: HIT-SCALED. - Otherwise fetches (or loads from cache) the original. - If w>0, the origin content-type is resizeable (contains "jpeg", "jpg", "png", or "webp"), and the source is decodable and wide enough (source width > targetW × 1.2): decodes, bilinear-scales to w px wide (aspect-ratio preserved), re-encodes as JPEG quality 85, caches the result, and serves it — Content-Type: image/jpeg, headers X-Original-Width, X-Resized-Width, X-Cache: MISS-SCALED. - Otherwise: serves the original bytes unmodified with the original’s own detected Content-Type, header X-Cache: HIT-ORIG. - All successful image responses additionally set Content-Length and Cache-Control: public, max-age=86400 (24 hours).

Response — errors: (plain http.Error text responses, not the JSON middleware.WriteError format) - 400 Bad Request — "url parameter required" (missing/empty url). - 400 Bad Request — "only http:// and https:// URLs may be proxied" (scheme not allowed). - 502 Bad Gateway — "upstream fetch failed: " + err.Error() (origin fetch failed).

Notes: Purpose is CSP/mixed-content mitigation — the app’s img-src CSP directive is restricted to 'self', so all external image URLs are rewritten to route through this endpoint rather than the browser loading them directly. Caching is two-tiered: an “original” cache keyed by source URL, and a “scaled” cache keyed by (URL, target width) for resized JPEG variants.

Cross-cutting notes for this section

  • Entity types (Public, LoggedIn, Team, User) and Resource types (Gallery, Display, Photo — deliberately no Exhibition resource type, since exhibition scope is the exhibitionid column instead) are exactly the string constants validated by the grants endpoints.
  • The permission-checking chain matches ownership-chain ancestors: Display chain = Global → Organization → Exhibition → Gallery → Display; Photo chain = Global → Organization → Exhibition → Photo (Photos are NOT under the Gallery chain). A grant at any ancestor tier satisfies a check at a descendant.
  • HasAny — used by every admin handler in this section — only ever checks the global/exhibition-level grant; it never inspects resource-scoped grants.
  • No self-lockout guard exists anywhere in these endpoints — e.g. removing PermAdmin from a role a caller is currently relying on, or revoking/deleting an admin’s own last admin grant, is not prevented anywhere in this code.
  • Singleton (__grant:-prefixed) roles are a purely additive per-user override mechanism used elsewhere in the app (e.g., the per-user private-photo-view toggle on the Users admin page) — none of the endpoints in this section create or revoke singleton grants directly; the Roles handlers only exclude them from listings/edits.

POST /auth/register

Category: Authentication Auth: not required (public) — creates a new local account. Headers: Content-Type: application/json expected; reads X-Forwarded-For for rate-limiting purposes (falls back to the raw connection address if absent/unparseable). Cookies: on success sets photoapp_session (Path=/, HttpOnly, SameSite=Lax, MaxAge=2592000). Request body:

{ "username": "string", "email": "string", "password": "string" }

email is trimmed and lowercased server-side; username is trimmed only (case preserved).

Response — success: 201 Created

{ "userid": "string", "username": "string", "email": "string" }

Response — errors: - 429 Too Many Requests — "Too many registration attempts. Try again in %.0f seconds." plus a Retry-After header. Rate limit is per-IP: the first attempt is allowed immediately; each subsequent attempt before the cooldown elapses is rejected, and the cooldown doubles every time an attempt is allowed — starting at 10 seconds and doubling from there. Records are cleaned up after 24 hours of inactivity. - 400 — "invalid JSON". - 400 — "username, email and password are required" — any of the three empty after trimming. - 400 — "password must be at least 8 characters" — byte length, not rune-aware. - 409 Conflict — "email or username already in use" — an existing non-deleted user matches (username case-sensitive, email compared after lowercasing). - 500 — "server error" — bcrypt hashing failure. - 500 — "registration failed" — INSERT failure (e.g. a race-condition unique-constraint violation not caught by the pre-check). - 500 — "session creation failed" — account was created but no session cookie could be issued.

Notes: Password hashed with bcrypt (DefaultCost). New user is inserted with provider='local' and a generated /avatars/<md5> profile image (not an uploaded image). No username-collision-avoidance/auto-suffixing here (unlike OAuth account creation) — a duplicate username is instead caught pre-flight and returns 409.

POST /auth/login

Category: Authentication Auth: not required (public) — the credential exchange itself. Permissions: the target account’s provider must be 'local' — OAuth-only accounts cannot log in via this endpoint. Headers: Content-Type: application/json expected. Cookies: on success sets photoapp_session (same attributes as Register). Request body:

{ "email": "string", "password": "string" }

The lookup matches (email = $1 OR username = $1) using the email field only — a caller can log in by putting either a username or an email address into the email JSON field; the request struct’s username field (shared with Register) is not used by Login at all. The identifier is lowercased and trimmed before lookup, making username-based login effectively case-insensitive even though usernames are stored case-sensitively at registration.

Response — success: 200 OK

{ "userid": "string", "username": "string", "email": "string" }

Response — errors: - 400 — "invalid JSON". - 401 — "invalid email or password" — no matching local-provider, non-deleted user found. The identical message is also returned for a bcrypt comparison failure, so a caller cannot distinguish “unknown identifier” from “wrong password.” - 403 — "this account has been disabled" — credentials were valid but the account is disabled; deliberately a distinct message from the generic 401 case. - 500 — "session creation failed".

Notes: No rate limiting on Login (unlike Register) — no brute-force throttling is applied here. The session token is 32 random bytes, hex-encoded, stored directly (not hashed, despite the storage column being named token_hash) in the sessions table alongside the user ID, a 30-day expiry, the requesting user agent, and IP address.

PATCH /auth/profile

Category: Authentication Auth: required — checked internally (not via the router’s auth() wrapper, since that only applies to /api/v1/...); 401 if no resolved user. Permissions: none beyond being authenticated (works for both local and OAuth accounts). Headers: Content-Type: application/json expected. Request body:

{ "profileImage": "string" }

Value is trimmed; must be non-empty and must start with /avatars/ or /uploads/ — arbitrary external URLs are rejected.

Response — success: 200 OK, {"profileImage": "<the accepted value>"}.

Response — errors: - 401 — "authentication required". - 400 — "invalid JSON". - 400 — "profileImage is required" — empty after trim. - 400 — "invalid profileImage URL" — doesn’t start with /avatars/ or /uploads/. - 500 — "db error".

Notes: Used to switch to a preset generated avatar or a previously-uploaded image. Does not touch the separate “source” image field — only the displayed profile_image is updated, so a user can switch back to their real photo later without having lost the record of it.

POST /auth/profile/avatar

Category: Authentication Auth: required — checked internally, same pattern as PATCH /auth/profile; 401 if no resolved user. Permissions: caller’s account provider must be 'local' (re-checked via a fresh DB query) — OAuth-provider accounts are forbidden from uploading a custom avatar. Headers: Content-Type: multipart/form-data required. Request body: multipart form with one file field: - image — required; max total form size 4 MiB.

Response — success: 200 OK, {"profileImage": "<new URL>"}.

Response — errors: - 401 — "authentication required". - 403 — "profile image upload is only available for local accounts" — non-local provider. - 400 — "could not parse form (max 4MB)" — multipart parse failure or size exceeded. - 400 — "image file is required" — no image field in the form. - 400 — "image must be PNG, GIF, WebP or JPEG" — content-type sniffing (first 512 bytes) didn’t match an allowed type; the file extension is derived from the sniffed type, not the original filename. - 500 — "could not create upload directory". - 500 — "could not save file".

Notes: File is saved under the configured upload directory with a fresh UUID-based filename (original filename discarded, avoiding path-traversal/collision concerns). Unlike PATCH /auth/profile, this endpoint updates both the displayed profile image and its “source” record, since the upload IS the new real source image. The DB write on success is not strictly checked for errors — the handler still returns 200 with the new URL even if that final DB update failed, meaning the uploaded file could in principle end up orphaned on disk with no DB record pointing to it.

Cross-cutting notes for authentication

  • Password hashing: bcrypt, default cost, used only for local Register/Login.
  • Session tokens: 32 cryptographically random bytes, hex-encoded, stored directly (not further hashed) in the sessions table alongside user ID, 30-day expiry, user agent, and IP address. Session validation requires: not revoked, not expired, user not soft-deleted, and account_enabled = TRUE — checked fresh on every request, so disabling or deleting a user invalidates all their existing sessions immediately without any explicit revocation step.
  • Username uniqueness: only OAuth account creation auto-resolves collisions (appending an incrementing numeric suffix, or a random suffix as a last resort). Local registration does not auto-resolve — it pre-checks and returns 409 Conflict on any collision.
  • Avatar handling: two independent fields — the currently-displayed profile image (may be a generated avatar or a locally-stored upload) and a separate “source” image (the original real photo, kept so a user can switch to a preset avatar without losing it). External OAuth provider photo URLs are downloaded and re-hosted locally, both at account creation and lazily on subsequent logins, to avoid loading third-party image URLs directly (CSP/mixed-content mitigation) — this only applies to Google and Facebook, since Apple and Microsoft never supply a picture URL.
  • OAuth account linking: if no user is found by the provider-specific ID, but an email is present, an existing non-deleted user with that email (regardless of their original provider) is silently linked to the new OAuth provider rather than creating a duplicate account. No additional ownership verification is performed for this linking step — it trusts the OAuth provider’s email claim entirely.
  • Disabled-account handling: enforced in two independent places — Login explicitly checks after password verification and returns a distinct 403, and session validation (used on every subsequent cookie-authenticated request, including after an OAuth login) filters out disabled accounts at the query level, silently treating their session as invalid rather than surfacing a specific error.
