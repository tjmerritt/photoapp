## Session 4 — Found and fixed the real bug: concurrent packages racing on one shared test database

### What was done
User ran the diagnostic (`psql` present, `-count=1 -v` to bypass caching) and every DB-backed test in `internal/handlers`, `internal/permissions`, and `internal/photoimport` failed — but `internal/db`'s own new DB-backed test didn't. That split is the tell: `go test ./...` runs each package's tests as a separate OS process, and **runs multiple packages concurrently by default** (the `-p` flag). All of these packages were pointed at the same `TEST_DATABASE_URL`, so several processes were hitting one physical database at once. Two races follow from that: (1) `testutil`'s `migrationsOnce` only dedupes *within* one process — every package's process independently re-ran all 17 migration files via `psql -f` against the same database at the same time, and Postgres's `CREATE TABLE IF NOT EXISTS` is not actually safe under true concurrency (two sessions can both see "not exists" and race to create it, one loses with a duplicate-object error); (2) even past migrations, `TruncateAll` running in one package's test would wipe tables a different package's test was mid-assertion on. `internal/db` likely just won that race often enough (small, fast-compiling package) to look clean, while the bigger packages collided — consistent with a nondeterministic race rather than a deterministic bug.

Fixed both layers:
- `internal/testutil/testutil.go`'s `applyMigrations` now opens one `pgx.Connect` and holds a Postgres advisory lock (`pg_advisory_lock`) for the entire migration run, serializing that specific step across any number of concurrent processes as defense in depth.
- The real fix: `Makefile`'s `test-go` now runs `go test -p 1 -count=1 ./...` — `-p 1` serializes package execution so only one package's tests (and therefore only one process's worth of truncation) touch the shared database at a time; `-count=1` bypasses Go's test cache, which has no way to know `TEST_DATABASE_URL` affects the outcome and would otherwise keep serving a stale result. Propagated the same flags into `scripts/githooks/pre-commit` and documented the *why* (not just the *what*) in both `TruncateAll`'s and `applyMigrations`'s doc comments and in `README.md`'s Testing section, since dropping `-p 1` silently reintroduces this exact bug.

### Testing notes
Same sandbox limitation as every prior session — no Go toolchain here. This one I'm more confident about than usual, though: the symptom (every test in a package fails uniformly and instantly, but not every package, and it wasn't reproducible from a single-package run) is close to a textbook description of a cross-process race, `pgx.Connect` + `pg_advisory_lock`/`pg_advisory_unlock` is a standard, well-worn pattern for exactly this problem, and `-p 1` is Go's documented, supported way to serialize package test execution. Please re-run — `make test-go` now bakes in both flags, or manually: `TEST_DATABASE_URL=... go test -p 1 -count=1 ./...`.

First package's process applies it fine; every subsequent package's process hits a real Postgres error trying to add a column that's already there.

- Queries `schema_migrations` for already-applied names before doing anything, skips any file already recorded, and inserts a row immediately after each successful `psql -f` run.

- Had to also exclude `schema_migrations` itself from `TruncateAll`'s truncate list (`internal/testutil/testutil.go`) — otherwise every test would wipe the tracking table even though the real schema changes persist, silently reintroducing the exact same "already exists" failure on the next package's process.

## Session 7 — Rejected the whole locking approach; redesigned around unique fixtures + shared schema

### What was done
Before Session 6's fix could even be confirmed, the user pushed back hard on the direction, correctly: "Holding a lock seems like a poor solution. The tests should be able to operate independently of each other and in parallel without failing." That's a fair critique of everything Sessions 4–6 had been doing — an advisory lock (package-scoped, then whole-test-scoped) doesn't make concurrent access *safe*, it just serializes access to one shared resource so nothing had to *be* safe. It also quietly took away the parallelism `go test ./...` is supposed to give.

Tried two replacement designs, in order, and the user rejected both, correctly:
1. **Wrap each test in its own DB transaction, rolled back at the end.** Standard pattern, but a `grep`-based audit (via a research subagent) found `internal/handlers/{teams,roles,upload}.go` all call `Pool.Begin` directly in production code. Wrapping the whole test in an outer transaction would turn those into nested transactions/savepoints under test but real top-level transactions in production — the user's objection: "Nested transactions isn't what we will encounter under production load." Correct — that divergence could hide real bugs. Dropped before implementing against test files.
2. **Give each test binary (≈ each package) its own private Postgres schema**, migrated once, no truncation, no lock. Implemented this fully (`db.NewWithSchema` with a pinned `search_path`, `testutil.createAndMigrateSchema`) before the user rejected it too: "Separate schemas seems like a terrible idea" / "It will not be reflective of actual usage." Right again — this app is multi-tenant (every resource scoped by `exhibitionid`), so production always has many concurrent callers sharing one schema; giving each test package a private schema means the tests stop exercising that property.

The user's actual instruction cut through both: **"Make sure you use distinct keys for each test and you should not have to worry about one test stomping on another."** That's the real fix — not infrastructure-level isolation at all, just making sure concurrent writers never collide, the same way concurrent tenants don't collide in production.

**Implemented**: reverted `internal/db/db.go` to its original single `New` function (no `NewWithSchema`). Rewrote `internal/testutil/testutil.go` from scratch: `RequireDB` now does nothing but skip-if-unset, connect, and a cheap `to_regclass('public.users')` sanity check that fails with a clear message if the target database hasn't been migrated — no `TruncateAll`, no automatic migration application, no lock of any kind. Migrating `TEST_DATABASE_URL` is now an explicit one-time step (`DATABASE_URL=$TEST_DATABASE_URL make migrate-up`), the same as any real deployment — not something tests do implicitly. The package doc comment lays out the reasoning at length, including why the two rejected designs were reverted, so nobody re-introduces them without re-reading why.

**Audited every existing DB-backed test file** for anything that would only have worked because of the old truncate-before-each-test behavior — the real risk in a shared, never-reset database. Found and fixed two real bugs this design would otherwise have shipped with:
- `internal/permissions/permissions_test.go`'s `TestCheck_GlobalGrant_AppliesToEveryExhibition` deliberately grants `PermAdmin` to `Public` with **no scope at all** — a genuinely global grant. Left in place, the first run of this test would permanently give every user in every exhibition `PermAdmin`, silently breaking every other test asserting "a plain user is forbidden from admin actions" (`TestTeamsHandler_List_RequiresAdminOrTeamAdmin`, `TestTemplatesHandler_Create_RequiresAdmin`, `TestHasAny_TrueIfAnyPermissionMatches`'s second assertion) for the lifetime of the test database. Fixed with `t.Cleanup` deleting the role, which cascades to the grant row (`entity_role_grants.roleid ... ON DELETE CASCADE`).
- `label_names` (migration `016_label_names.sql`) is a global catalog keyed by `name` alone — not exhibition-scoped like nearly everything else. Two tests inserted hardcoded literal names directly (`'Sensitive'` in `labels_test.go`, `'Location'` in `photoimport/exif_test.go`), which would collide with themselves on any second run once nothing truncates the table between runs. Fixed both to use `"<label>-" + uuid.NewString()`. (A third test, `TestMarkNamesRestricted_UpsertsAndSkipsEmptyNames`, reuses fixed names `"Camera Make"`/`"ISO"` too — left alone after checking `MarkNamesRestricted`'s actual SQL: it's a real `ON CONFLICT (name) DO UPDATE` upsert, so repeated runs are genuinely idempotent there, unlike the other two which used a plain `INSERT`.)

Checked every other DB-backed test file (`photo_test.go`, `comments_test.go`, `teams_test.go`, `templates_test.go`, `emojis_test.go`) for unscoped list/count assertions against tables another concurrent test could also be writing to. All were already either scoped by a specific `exhibitionid`/`photoid`/`teamid` the test itself created, or (in `teams_test.go`/`templates_test.go`) already written as "find my own row in the list" rather than an exact global count — no further fixes needed there. `templates_test.go` in particular already knew `display_templates` is global (its own comment says so) and had already used `uuid.NewString()` in template names and a found-in-list check rather than an exact count, so it needed no changes.

Updated `Makefile` (`test-go` is now plain `go test -count=1 ./...`, no `-p 1`), `scripts/githooks/pre-commit` (same), and `README.md`'s Testing section to describe the new shared-database, no-lock, no-truncation model and the migrate-once setup step.

## Session 12 — real production bug found by TestEmojisHandler_ListVariants: fixed EmojisHandler.ListVariants

### What was done
User ran the Session 11 suite: everything passed except `TestEmojisHandler_ListVariants`, with the server logging `ERROR: column "sort_order" does not exist (SQLSTATE 42703)`. This is not a test-authoring mistake — it's `EmojisHandler.ListVariants` (`internal/handlers/emojis.go`) itself being broken in a way no prior test had ever exercised, exactly the kind of thing this whole "test the testing tools, then fill in the real gaps" push was for.

Root cause: the handler's query is a `UNION ALL` of two `SELECT`s (base emoji, then skintone variants), with a trailing `ORDER BY sort_order, created_at`. Postgres resolves a `UNION` query's `ORDER BY` against the *combined result's output column list*, not the underlying tables — and neither `SELECT` in this query actually selected `sort_order` or `created_at`. That's valid to write (Postgres doesn't reject it at parse time if the column happens to not exist anywhere in scope for the union), but here it fails at execution because `sort_order`/`created_at` aren't visible in that scope at all. This had zero coverage before Session 11 (0% per every prior `go tool cover -func` report), so it had presumably never actually been called with a hexcode that had any matching rows — my `TestEmojisHandler_ListVariants` was the first thing to ever exercise the query end-to-end with real data.

**Fix** (`internal/handlers/emojis.go`, `ListVariants`): added `sort_order, created_at` to both `SELECT`s' output lists so `ORDER BY` can resolve them, and added two throwaway scan targets (`rowSortOrder int`, `rowCreatedAt time.Time`) to the existing `Scan` call to match the now-wider result set — the response shape (`models.EmojiTypeResponse`) is unchanged, this is purely an internal query fix. Added `"time"` to the file's imports. Documented in a comment directly above the query why the columns have to be there even though nothing in Go ever reads them back out.

No code changes this session; read `auth.go`'s full OAuth surface (`googleConfig`/`GoogleLogin`/`GoogleCallback`, `AppleLogin`/`AppleCallback`/`validateAppleIDToken`/`appleJWKToRSA`, `facebookConfig`/`FacebookLogin`/`FacebookCallback`, `microsoftEndpoint`/`microsoftConfig`/`MicrosoftLogin`/`MicrosoftCallback`) and `cmd/server/main.go`'s `AuthHandler` construction to ground the analysis in the actual code rather than give generic advice.

**Findings**: Google, Facebook, and Microsoft are structurally identical (~130 duplicated lines each) — build an `oauth2.Config`, redirect with a CSRF `state` cookie, on callback validate `state`, exchange the code for a token, GET a provider-specific userinfo URL, unmarshal a provider-specific JSON shape into `(sub, email, name, picture)`, then hand off to the already-shared `findOrCreateOAuthUser` → `localizeExternalProfileImage` → `finishLogin`. Apple is structurally different (cross-site `response_mode=form_post` callback, JWT/JWKS validation instead of a token exchange + userinfo call, its own CSRF cookie with `SameSite=None; Secure`) but shares the identical back half once an identity is resolved.

**Proposed design** (not implemented): an `OAuthProvider` interface — `Name() string`, `Configured() bool`, `AuthURL(state string) string`, `Exchange(ctx, r *http.Request) (ExternalIdentity, error)` — with `ExternalIdentity{Sub, Email, Name, Picture}`. Real `googleProvider`/`facebookProvider`/`microsoftProvider` wrap the existing `oauth2.Config` + userinfo fetch; `appleProvider` wraps the JWT/JWKS validation. `AuthHandler` would carry the providers as a field (defaulting to real ones when built from `config.Config`, so `main.go`'s one-line construction wouldn't need to change), collapsing Google/Facebook/Microsoft's `Login`/`Callback` pairs into one generic implementation while Apple keeps its own thin wrapper for the form-post/cookie quirk but delegates identity resolution through the same interface. This puts the DI seam exactly at the security-relevant boundary — "did we correctly verify this token/code and resolve who it belongs to" — so a `fakeProvider` in tests can script identities/errors and exercise the entire currently-0%-covered decision tree (new user, re-login by same `sub`, account-linking by email, CSRF state mismatch, not-configured, exchange failure) through the real handler code, with the real per-provider verification logic tested separately and more narrowly against fake token/JWKS servers.

Offered a lighter alternative too (leave the four provider functions structurally as-is, just make the hardcoded endpoint/userinfo/JWKS URLs overridable so tests can point them at `httptest.Server`s — smaller diff, no de-duplication benefit, messier tests) and flagged the interface refactor's real trade-off honestly: it changes production authentication code, not just test infrastructure, so even with full new test coverage it would still want one manual smoke-test pass against real Google/Apple/Facebook/Microsoft accounts before trusting it, since a mock can't confirm the real implementations still satisfy each provider's actual handshake.

**Decision**: user chose to defer. Logged as task #28 in the session task tracker with the design notes above, to be picked up as its own properly-scoped piece of work rather than folded into Phase 0's test-backfill effort.

## Session 20 — Fix non-idempotent migrations 018 and 021

### What was done

- `018_grant_exhibitionid.sql`: `ADD COLUMN exhibitionid` → `ADD COLUMN IF NOT EXISTS exhibitionid`. `ADD CONSTRAINT chk_exhibitionid_resource_exclusive` had no guard at all (inconsistent with the very next constraint down, `entity_role_grants_resource_type_check`, which already did `DROP CONSTRAINT IF EXISTS` first) — fixed, but not with a plain `DROP IF EXISTS` + re-`ADD` like that one, because `021_org_admin.sql` later permanently retires this exact constraint (drops it and replaces it with `chk_grant_scope_exclusive`). END IF; END $$;` so 018 only resurrects its own constraint when 021 hasn't already superseded it.

## Session 22 — Root-caused and fixed: "random" admin page results

### What was done
User reported admin pages randomly showing a successful load, "You are not a member of any exhibitions," or "You don't have admin access, or the server needs to be rebuilt" — inconsistently, on repeated reloads of the *same* page. Ruled out staleness first (asked the user directly: migration applied, server rebuilt, and seed script all confirmed done), and the user separately narrowed the failure pattern to "same page, different result on reload" — which rules out a per-page wiring bug and points squarely at a race condition, matching the user's own guess that it was a JS race between the org/exhibition fetches.

Found the actual root cause in `alpinejs.min.js` itself, not in the fetch logic: every page in this app has always had `<html x-data="pageComponent" x-init="init()">` — but Alpine has a built-in "magic init()" feature (confirmed by grepping the bundled `alpinejs.min.js` for `hasOwnProperty("init")&&typeof e.init=="function"&&rt[t].init()`): if the object returned by an `x-data` factory defines a method literally called `init`, Alpine calls it *automatically* the moment the component initializes — no `x-init` needed. Every single page component in this codebase (`wallApp`, `photoApp`, `adminMaster`, all others — verified via grep that all 14 top-level components plus `photo.html`'s two nested modal components, `labelEditor`/`emojiPicker`, each define their own `init()`) already relies on this. The explicit `x-init="init()"` alongside it was pure redundancy — meaning **every page's `init()` has always fired twice, concurrently**, on every load.

This was latent/harmless everywhere else in the app, since most `init()` implementations either did cheap, idempotent work or didn't have two overlapping async chains racing to write the *same* shared, page-visible state. Phase 1d's `loadAdminScope()` changed that: it's a multi-step async chain (`/auth/me` → `/api/v1/admin/organizations` → `/api/v1/admin/org-exhibitions`) that writes directly to `authError`/`noExhibitions`/`organizations`/`exhibitions`/`selectedExhibition` on `this`. With `init()` firing twice, two independent copies of that whole chain ran concurrently against the same live component, both racing to write those same fields — whichever call's promises happened to resolve last won, regardless of which one actually reflected the correct/successful outcome. That's exactly "same page, different result on reload": the winner was decided by network/DB timing on each individual page load, not by any actual difference in server state.

**Fix**: removed the redundant `x-init="init()"` everywhere it duplicated Alpine's own automatic init call — 17 occurrences across 15 files (`admin-emojis.html`, `admin-labels.html`, `admin-master.html`, `admin-permissions.html`, `admin-roles.html`, `admin-teams.html`, `admin-users.html`, `admin.html`, `display-edit.html`, `display.html`, `galleries.html`, `gallery-admin.html`, `index.html`, `template-admin.html`, and `photo.html` — the last one three times: its own top-level `<html>` tag plus the `labelEditor`/`emojiPicker` modal `x-data` elements). Verified before removing any of them that each corresponding factory function actually defines an `init()` method (grepped `app.js`/`admin.js` for all fourteen top-level names plus the two nested ones) — Alpine's magic init only fires for objects that define one, so this would have silently broken initialization entirely on any component that *didn't* have its own `init()`. None were missing.

### Testing notes
No live browser/server available in this sandbox to reproduce the race directly, but the mechanism is confirmed straight from Alpine's own minified source (not inference from symptoms alone). Verified: `bash -n` equivalent via re-reading each edited file; div-tag balance counts unchanged across all 15 touched HTML files (no accidental markup damage from removing the attribute); `bash scripts/build-tailwind.sh` still compiles cleanly; `npx vitest run` still 19/19.

### Open items
- User should confirm the fix by reloading an admin page repeatedly (the same test that surfaced the bug) and seeing a consistent result every time now.
- This was a pre-existing, app-wide latent bug (not introduced by Phase 1d) that Phase 1d's heavier `init()` simply made visible. Worth keeping in mind for any future page: Alpine's magic `init()` means `x-init="init()"` should never be added alongside a component that already names its bootstrap method `init`.

## Session 23 — Root-caused and fixed the remaining "random" admin page failures: a real Postgres SQL bug, not a JS race

### What was done
After Session 22's double-`init()` fix, the user reported the admin pages were still failing "randomly," just less often, and narrowed it to exactly the six pages that use the header org/exhibition picker (overview, photos, users, teams, permissions, roles). The user then supplied the actual smoking gun from the server log: `"msg":"ListOrganizations global check","error":"ERROR: invalid input syntax for type uuid: \"\" (SQLSTATE 22P02)"`.

That log line traces directly to `scope.go`'s `ListOrganizations`/`ListExhibitions` calling `Checker.Check(ctx, userID, "", "", "", "", permissions.PermAdmin)` — the picker's "is this user a global admin" probe, which deliberately passes `exhibitionID=""`. `Checker.Check`'s SQL (added in Phase 1c) had a `LEFT JOIN exhibitions ex ON $3 <> '' AND ex.exhibitionid = $3::uuid` clause meant to guard the `$3::uuid` cast so it would never run against an empty string. That guard does *not* reliably work inside a JOIN's ON clause: Postgres does not guarantee left-to-right short-circuit evaluation of an AND there the way it effectively does for a simple WHERE-clause filter, and — more concretely — pgx/Postgres prepared statements switch from a per-call "custom" plan (built using the actual bound parameter values) to a cached "generic" plan after roughly five executions of the same statement; the generic plan doesn't know $3 will be empty and can evaluate `$3::uuid` unconditionally, throwing exactly this error. This also fully explains the "randomness": pgxpool has multiple connections (min 2, max 20), each with its own independently-tracked prepared-statement plan cache, so whichever pooled connection happened to serve a given request determined whether that connection had already flipped to the failing generic plan. Not a JS race at all — a deterministic-per-connection SQL bug, made to look random by connection pooling. (Session 22's fix was still worth doing — halving concurrent request volume did reduce how fast each connection's execution count reached the generic-plan threshold — but it wasn't the root cause.)

**Fix**: replaced every `$N <> '' AND ... = $N::uuid` guarded-cast pattern in the affected queries with `... = NULLIF($N, '')::uuid`. `NULLIF($N, '')` evaluates to SQL `NULL` when the parameter is an empty string, and `NULL::uuid` always succeeds (there's nothing to parse), so this is safe regardless of query plan or evaluation order — it doesn't rely on short-circuiting at all. Fixed in `internal/permissions/permissions.go`: the `LEFT JOIN exhibitions` in both `Check()` and `UserPermissions()`, plus the parallel `erg.exhibitionid = $N::uuid` OR-branches in each (5 sites total). Also swept `internal/handlers/emojis.go` for the identical pattern, since it uses the same "guarded organizationid cast" idiom on every emoji list/catalog endpoint (`ListTypes`, `AdminListTypes`, `ListVariants` — 4 sites) — these hadn't been reported broken yet but are exposed to the exact same risk on every wall/photo page load, an even hotter path than the admin pages. Updated the doc comment above `Check()` to explain why `NULLIF` is required instead of the guard idiom, referencing this session.

### Testing notes
No live Postgres/browser available in this sandbox (no network access to install a Go toolchain or Postgres either), so this was verified by careful manual review of each diff rather than a build or live query — confirmed the `NULLIF` rewrite preserves the original semantics in both directions: empty string → NULL → comparison never matches (same as the old guard's intent), non-empty string → cast proceeds exactly as before. Re-grepped the whole repo afterward for the `<> '' AND ... = $N::uuid` pattern and confirmed zero remaining occurrences outside of comments.

### Open items
- Ask the user to reload the six admin pages repeatedly and watch the server log for the same `SQLSTATE 22P02` error — it should no longer appear at all now, not just less frequently.
- The same "generic plan" risk theoretically applies to any other guarded cast pattern in the codebase that wasn't caught by the `<> '' AND ... ::uuid` grep (e.g. differently-shaped guards over non-uuid casts); none were found, but worth keeping in mind if a similar error surfaces elsewhere.
- **Superseded by Session 24**: the "custom vs. generic plan" explanation below turned out to be wrong (or at least not the operative mechanism) — the user confirmed a direct DB connection and a genuine full rebuild/restart, and the exact same error, from the exact same log tag, still occurred afterward. ## Session 24 — The NULLIF fix wasn't enough either: the real root cause was parameter *binding*, not query evaluation

### What was done
The user reported the identical error (`"msg":"ListOrganizations global check","error":"ERROR: invalid input syntax for type uuid: \"\" (SQLSTATE 22P02)"`) still occurring after Session 23's `NULLIF` fix — less often (down from roughly 3 in 4 to roughly 1 in 4), but not gone. Ruled out the obvious mundane explanations first, by asking directly: the DB connection is direct to Postgres (no PgBouncer/RDS Proxy/other pooler in between, which would have been a strong alternate suspect), and the server was fully killed and rebuilt, not hot-reloaded. A follow-up log line pinned the exact request: `GET /api/v1/admin/organizations?limit=20` → `status 500`, `duration_ms 0` — failing essentially instantly, before any real query work, which is the tell for a failure at parameter-binding time rather than during query execution.

That reframes the whole diagnosis. Postgres (via the extended query protocol pgx uses) infers each `$N` placeholder's type once, from how it's used across the *entire* prepared statement. `$2`/userID in `Check()`/`UserPermissions()` is safe with a bare `NULLIF($2, '')::uuid` because it also appears elsewhere in the same query compared directly against a text column (`erg.entity_ref = $2`), which anchors its inferred type to `text`. `$3`/exhibitionID has no such anchor — *every* occurrence of it in the query is inside a `::uuid` cast — so Postgres infers `$3`'s own parameter type as `uuid`. That means the empty string has to be parsed as a uuid the instant pgx binds the parameter, which happens before the query body executes at all — before `NULLIF`, before any `CASE`, before any SQL-level guard gets a chance to run. This is also why displays.go's `NULLIF($2::text, '')::uuid` pattern (explicit `::text` first) has always worked correctly: the explicit cast pins the parameter's inferred type to `text` directly, sidestepping the whole problem, whereas `NULLIF($1, '')::uuid` with no other anchor does not.

**Fix**: stopped trying to solve this in SQL at all. Added a `nullableUUID(s string) any` helper (in `internal/permissions/permissions.go` and, separately, `internal/handlers/pagination.go` since the two packages don't share a helpers file) that converts `""` to a real Go `nil` before it reaches pgx — a `nil` argument becomes an actual SQL `NULL` on the wire, which never goes through the uuid input parser regardless of the parameter's inferred type, since there's no text to parse. Reverted the `NULLIF($N, '')::uuid` sites back to plain `$N::uuid` (no SQL-side trick needed at all now) and pass `nullableUUID(...)` as the Go argument instead, in:
- `permissions.Checker.Check` and `UserPermissions` (the confirmed-failing sites, and their sibling `erg.exhibitionid = $N::uuid` OR-branches)
- `emojis.go`'s `ListTypes`, `AdminListTypes`, `ListVariants` (organizationid reads) and `UploadType` (organizationid write — an emoji upload with no organization scope is a completely normal case)
- `displays.go`'s `Update` (templateid — "" legitimately means "clear the template", per the handler's own comment) and its slot-upsert (photoid — "" legitimately means "clear this slot's photo")
- `admin_grants.go`'s grant `Create` and `Update` (exhibitionid — an organization-level or global grant legitimately has no exhibitionid; this is a Phase 1c addition, so these two sites may well be part of what's been intermittently breaking the Permissions admin page specifically)
- `upload.go`'s photo insert (exhibitionid, lower risk since uploads should always have a resolved exhibition, but fixed for consistency)

Left alone, deliberately: `permissions.go`'s two userID team-membership subqueries (anchored to `text` elsewhere in the same query, per the mechanism above — and empirically never reported broken despite heavy anonymous traffic), `displays.go`'s template-lookup `NULLIF($1,'')::uuid` at line ~340 (only ever called from inside a Go `if *req.TemplateID != ""` guard, so never actually reachable with an empty value), and `cmd/import-photos/main.go`'s equivalent (a batch CLI tool with exhibitionid always supplied via flag, out of scope for this bug).

Still no live Postgres/Go toolchain available in this sandbox to build or run against a real database, so this was verified the same way as Session 23: careful line-by-line diff review, confirming each `nullableUUID(...)` call site replaces exactly the argument that used to carry `""`, and that every corresponding `NULLIF($N, '')::uuid`/`$N <> '' AND ... ::uuid` in SQL was simplified back to a plain `$N::uuid` consistently at each touched site. Re-grepped the whole repo for `NULLIF\(\$\d+,\s*''\)::uuid` afterward and confirmed only the three deliberately-left-alone sites above remain.

## Session 28 — Phase 2b bug fix: `ListPhotosHandler` leaked private photos to anonymous users

### What was done
User ran `go test -p 1 -count=1 ./...` and got a real, reproducible failure: `TestListPhotosHandler_OnlyPublicVisibleToAnonymous` got both the public and the private test photo back for an anonymous request, instead of just the public one. Exactly the kind of thing manual review without a compiler/DB is prone to miss.

Root cause: `photoIsPublicSQL`'s `EXISTS` subquery is `SELECT 1 FROM labels pub WHERE pub.photoid = <photoIDExpr> AND pub.name = 'Public' AND pub.value = 'True' AND pub.deleted_at IS NULL`. `ListPhotosHandler.ServeHTTP`'s query (`internal/handlers/photo.go`) was the one call site still passing the bare, unqualified `"photoid"` as `photoIDExpr` — its outer query was `FROM photos` with no table alias. But `labels` (the subquery's own table) *also* has a `photoid` column. Postgres resolves an unqualified column reference in a subquery against that subquery's own range tables first; since `pub` (aliased or not) exposes a column literally named `photoid`, the right-hand side of `pub.photoid = photoid` resolved to `pub.photoid` itself — not the outer `photos` row — collapsing the correlation into `pub.photoid = pub.photoid`, which is trivially true for any row at all. Net effect: as soon as *any* photo anywhere had a `Public`/`True` label, the `EXISTS` returned true for *every* row in the outer query, regardless of that row's own visibility. Every other call site (`photo.go`'s other two queries, `fetch.go`, `search.go`, `admin.go`) was already passing the qualified `"p.photoid"`, which binds unambiguously to the outer alias and isn't affected — this was a single-site bug, not a bug in the helper itself.

Fixed by aliasing the outer table (`FROM photos p`) and qualifying every column reference in that query (`p.deleted_at`, `p.exhibitionid`, `p.owner_userid`, `p.created_at`, `p.photoid`), matching the pattern already used everywhere else, and calling `photoIsPublicSQL("p.photoid")`.

### Testing notes
Diagnosed from the user's actual test failure output (not hypothetical) — traced the exact SQL Postgres would generate for the failing query, confirmed `labels` has its own `photoid` column (migration 001) making the shadowing possible, and confirmed by grep that every other `photoIsPublicSQL` call site already passes an alias-qualified expression and was never at risk. Still no live DB/Go toolchain in this sandbox to actually re-run the failing test — the fix is a direct, mechanical correction of the exact mechanism identified, but the user re-running `go test -p 1 -count=1 ./...` is the real confirmation step.

### Open items
- Re-run the full suite and confirm `TestListPhotosHandler_OnlyPublicVisibleToAnonymous` (and the rest of the previously-passing suite) now passes.
- Worth a standing note for future `fmt.Sprintf`-built SQL in this codebase: any helper that correlates a subquery back to an outer row via a bare column name is only safe if the outer table is aliased and every call site passes the qualified form — an unaliased outer table whose column name happens to collide with a name inside the injected subquery will silently mis-bind rather than error. `photoIsPublicSQL`'s own doc comment already models the expected call shape (`"p.photoid"`) but doesn't explicitly warn against passing a bare name — could tighten that if this class of bug recurs.
